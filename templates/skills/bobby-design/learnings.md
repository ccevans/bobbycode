# Bobby Design — Learnings

This file accumulates anti-patterns and best practices discovered while designing. Check this file before starting work.

## Anti-Patterns
<!-- New learnings are added below this line by `bobby learn bobby-design "pattern" "description"` -->

- **Jumping straight to a full comp.** Skipping style tiles means the first thing the user sees is an expensive build in a direction they may not want. Always settle the visual language first.
- **Asking the user to make design decisions.** "What font do you want?" stalls a non-designer. Ask them to react, not to author.
- **One reference.** Copying a single site produces a derivative page. Always remix 2–4, and diverge through the subject's own world.
- **Three tiles that are one tile.** Producing three off-white-and-ink directions that differ only in warmth is not a set of options — it is one option at three temperatures. Different grounds, different type strategies, different motifs, or it does not count. Apply the description test.
- **Copying the restraint instead of the thinking.** When the user's references are minimal sites, taking the off-white ground produces the AI default. What those sites actually have is a specific point of view and real typefaces. Restraint without specificity reads as "nothing was decided."
- **Captioned signature moves.** Writing "the crew roster is the spine of the page" under a plain text list does not make it so. If the idea has to be explained, the design has not expressed it — render it structurally or drop it.
- **Passing your own checklist by feel.** Self-scoring a page as "fine" is how the generic version ships. Run the avoid-list literally, item by item, against what is actually on screen.
- **Skipping the reference step after feedback.** Getting told "this looks generic" creates pressure to jump straight to a bolder motif. That skips step 2 entirely and produces invented directions — bolder, but no better grounded. Feedback means go *back* to references, not past them.
- **References from memory.** "Film end credits," "greenbar computer paper," "Swiss posters" sound specific but are mental images. Working from a remembered aesthetic yields a generic imitation of it. If it was not looked at, it is not a reference — go find real specimens.
- **Unattributed motifs.** If a direction cannot name where it came from, it was invented from taste. Every tile carries its sources, visibly.
- **Keeping agreed decisions in conversation instead of a file.** This is the root cause of nearly every drift. Each rebuild re-derives values from memory, memory is lossy, and the design wanders until it no longer resembles what was agreed. Write `design-spec.md`, build from the file, and diff the build against it before publishing. A value in the build that is not in the spec is drift, not a decision.
- **Framing a mockup in a colour you are asking the user to judge.** A warm off-white shown against pure-white browser chrome reads as white, and the user will reasonably report it as such. When feedback contradicts what you built, check the presentation before assuming the feedback is wrong — and check the actual values before assuming it is right.
- **Leaving holes in the teardown.** Wherever a field is blank, your own taste fills it silently — which defeats the entire point. Every dimension is either extracted or explicitly marked `unknown — <why>`. There is no third state, and the transitions/feel row is the one most often left blank.
- **Scroll-linked effects inside an auto-height iframe.** The document can't scroll itself — the parent does — so neither `scroll` events nor IntersectionObserver ever fire inside it. Sticky-media-with-changing-content, scroll progress bars and parallax are impossible there, not merely fiddly. Detect it (`scrollHeight <= innerHeight`) and degrade on purpose, or the effect freezes on whatever state it guessed at load.
- **Checking the environment once at startup.** An auto-height frame begins tiny and is resized afterward, so any capability check that runs on load reads the wrong answer and never corrects. Re-evaluate inside the sync loop and listen for `resize`.
- **Copying a metaphor's components but not its staging.** Building an "the site is a desktop OS" direction with window chrome and an icon sidebar produced a page with a title bar — not a desktop. What makes a metaphor legible is the *framing*: a real wallpaper visible on all sides, a window that floats rather than going full-bleed, furniture that only exists in that world (taskbar, menu bar, icons on the wallpaper), and one cheap give-away like a second window peeking out behind. Build the staging first, the details second, and apply the 3-second test — could a stranger name the metaphor unprompted?
- **Pinning the visual but letting the copy scroll past it.** If the reference presents a fixed composition that *changes state*, both halves must be pinned and swap together. A sticky image with copy flowing past it is a different effect entirely and reads as an ordinary scrolling page. Drive it from scroll progress through a tall spacer so the two can never drift apart.
- **Scrolling past N copies of the hero object instead of pinning one.** If the reference keeps a device fixed and swaps its screen, reproducing that as a list of N devices scrolling by loses the entire feel. Pin it with `position:sticky` and change the content.
- **Viewport units and scroll-snap inside an auto-height iframe.** Artifact runtimes and embed hosts size the frame *from* the content's `scrollHeight`, which makes `100vh`/`svh`/`dvh` self-referential, leaves `scroll-snap` with no scroller to attach to, and lets `height:100%; overflow:hidden` collapse the frame entirely. None of it reproduces standalone. Size sections by content or a `px` min-height, let the host page scroll, and never lock overflow globally.
- **Assuming "not updating" means caching.** Fetch the served page and check whether your CSS is actually there before blaming a cache. Three rounds of "mobile" fixes deployed correctly and still failed, because the real cause was the delivery context (an auto-height iframe), not stale bytes. Verify what is live, then compare it against how it is being *delivered*.
- **Testing standalone when the page ships embedded.** A build can measure perfectly on its own and be completely broken in an iframe. Serve over HTTP (a `file://` iframe blocks cross-document access) and assert the frame height settles instead of climbing.
- **Building desktop-first and hiding it on mobile.** If the desktop layout is the default and mobile is the exception, then *any* failure of the media query — stale CSS, an unexpected layout viewport, iframe sizing — leaves a phone rendering the desktop layout, often with `overflow:hidden` making it unscrollable. Invert it: the simple always-works layout is the default, desktop is the `min-width` enhancement. Never make the fragile layout the fallback.
- **Forgetting that users see cached CSS.** A device screenshot showing a bug you already fixed usually means a stale cache — say so and ask for a hard refresh, but also check whether the reported symptom reveals a real fragility underneath. It often does.
- **Hiding content in CSS and relying on JS to reveal it.** `opacity:0` + IntersectionObserver strands the entire page invisible if the observer never fires — which happens inside iframes, with blocked scripts, or on engines that behave differently from the test browser. Content must be **visible by default**; apply the hidden state from JS (an `html.js-*` class) and add a timeout failsafe. Test with JavaScript disabled.
- **Nested scroll containers and `dvh` on iOS.** `body{overflow:hidden}` wrapping an inner `height:100dvh` scroller is unreliable in Safari, especially inside an iframe — the page simply won't scroll. Scroll the **document** instead (`scroll-snap-type` on `<html>`), scope `overflow:hidden` to desktop only, and layer `100vh` → `100svh` rather than reaching for `dvh`.
- **Assuming the test browser is the target.** Headless Chromium in a plain page does not reproduce iOS Safari inside an iframe. When a user reports a device bug you cannot reproduce, look for **fragile dependencies** — JS-gated visibility, nested scrollers, newer viewport units — and remove the fragility rather than trying to reproduce the environment.
- **Confusing "no overflow at 375px" with "works on mobile."** Geometry is not behaviour. A page can measure perfectly and still be dead to the touch because its interaction model is desktop-only. Drive the actual interaction in the harness — scroll it, tap it — not just measure it.
- **Wheel-driven navigation on mobile.** Touch scrolling never fires `wheel`, so any state-switcher built on it silently does nothing on a phone. Give touch a real path — usually native scroll with `scroll-snap` — which is why references using a fixed desktop stage ship a **separate mobile DOM tree** rather than restyling the desktop one.
- **Trusting media queries instead of rendering mobile.** Most layout bugs exist only at 375px and none are visible in source. Render at 375 / 768 / 1440 and assert `document.scrollWidth === viewport width` at each. Content inside its own `overflow-x:auto` container is the one legitimate exception.
- **Specificity collisions inside the media query.** A desktop `.cp.on { transform: translateY(-50%) }` out-specifies a mobile `.cp { transform:none }`, so the active element keeps its desktop transform and overlaps whatever is above it. Reset at matching specificity: `.cp, .cp.on { transform:none }`. Invisible in source, obvious in a screenshot.
- **Fixed-width grid columns on mobile.** `grid-template-columns: 190px 1fr` does not collapse by itself — it just crushes the content column. Add a single-column rule or drop the sidebar.
- **Testing a local file without injecting the viewport meta.** The browser falls back to a 980px layout viewport and every mobile measurement is meaningless.
- **Not screenshotting your own build.** You render the reference because source lies about what a page is — your own build lies identically. One round caught a hero clipping the product window it was meant to overlap, and an illustrated character hidden entirely behind a panel. Neither is visible in source; both would have shipped.
- **Guessing the fidelity level.** "Inspired by" and "make it look like that" are different jobs, and landing halfway reads as neither. Users who supply their own references usually want a close replica and will call anything looser "only 50% there." Ask, and default closer than feels comfortable.
- **Letting the reference's character stop at the fold.** A rich atmospheric hero followed by a plain white page is the classic half-finished result. Colour, illustration and motion belong in the body and the closing CTA too, at lower intensity.
- **Terminal text standing in for a product screenshot.** It reads as a placeholder. Build real interface — window chrome, sidebar with an active state, rows with IDs and status pills.
- **`01` / `02` / `03` on a row of cards.** A top-tier AI tell. Three parallel features are not a sequence, so the numbers carry no information — they just signal a template. Number only what must be done in order.
- **Guessing which side content sits on.** Rendering rfeasley showed the left column holds only the name and the *content* sits in the right column — the opposite of what was built from source. Column order in the DOM is not visual hierarchy. Look at the picture.
- **Not rendering the page. This is the single biggest failure mode in this skill.** A teardown done entirely from `curl` reported "pure white ground, restrained palette, no motion, Inter headings." The real page was a full-bleed illustrated dusk-sky gradient with animated flickering stars, a robot character, and a large editorial serif. Wrong on every axis, with a citation for each error. **Screenshot the page and read the image before writing a single line of teardown.**
- **Reporting a negative from static HTML.** Greps over a JS-rendered shell return near-empty results, and empty reads as "the design doesn't have this." Absence of evidence in source is not evidence of absence in the design. Never write "no motion" or "restrained palette" from source — only from the render, or mark it `unknown`.
- **Leaving `var(--token-<uuid>)` unresolved.** That is not a value. Unresolved indirection is `unknown`, not absent — and treating it as absent silently deletes the reference's entire palette.
- **Counting backgrounds by frequency instead of reading them in document order.** Frequency says "mostly white." Document order says "alternates white / #F7F7F7 band to band." Only one of those is the design, and it is never the histogram.
- **Skipping the shadow grep.** `box-shadow` is the highest-signal single grep on a polished site — a `0 0 0 5px #F7F7F7` ring is a photo mat around screenshots, and multi-layer fractional shadows are deliberate physical modelling. This is where craft hides, and it is invisible in a token list.
- **Ignoring image dimensions.** A 2592×1676 image is a product screenshot and probably the entire point of the page; a 184×2 is a divider. Dimensions separate the anchor from the decoration in one grep.
- **Grepping a Framer/Webflow site for its "design system."** These builders emit thousands of generated inline styles; frequency-counting them describes the renderer, not the design. The output — a font list, a background colour, some radii — looks like a successful extraction and produces a completely generic page. If the HTML is 300KB+ with no linked `:root` stylesheet, switch to a visual teardown and label it as such.
- **Building from a teardown whose Layout / Anchor / Transitions rows are empty.** A palette plus a font stack is not a design. This failure looks like success because every value is citable — and the result still resembles nothing the user pointed at.
- **Extracting tokens and calling it a teardown.** Colours and fonts are paint, not architecture. A palette tells you nothing about the fact that text sits in a 20% left column and a device mockup anchors a 55% centre stage. Layout usually lives in **inline styles** — grep the HTML, not just the CSS — and write down the exact column proportions, the visual anchor, and where the deliberate empty space is.
- **Ignoring motion and feel entirely.** "Has animations" is not a finding. "Copy cross-fades over 500ms while rising 12px, and pagination dashes stretch 6px → 20px over 350ms" is. Durations, easings, and distances are inheritable design; keyframe names are not.
- **Vetting only tokens.** People notice layout and feel first and usually cannot name a hex code. A vetting list made of colours and fonts asks about the dimension they care least about. Cover layout, motion, colour/type, and structure.
- **Padding the user's reference set with your own picks.** If they sent two references, two is the set. Adding a third "for range" is your taste re-entering wearing a citation — every value extracted from your own pick is a value you chose. The 3–5 target applies only when the user supplied none. If you think more range would help, ask; don't add.
- **Assuming how multiple references should be used.** Separate mockups per reference and a combined direction are different jobs with different output. Ask which; assuming a blend produces a design that matches none of the references and traces to none of them.
- **Assuming extraction tells you what the user liked.** It tells you what the reference *does*. Those are different. Vet the extracted traits with them in plain language before building, or you will honour a trait they never noticed and drop the one that made them send the link.
- **Claiming a design came from references it did not come from.** Fetching a site for prose impressions and then narrating a connection afterward is post-hoc justification — worse than admitting there was no grounding, because it dresses invention up as method. If the values did not come from the reference, say so.
- **Using a markdown-converting fetch tool for a teardown.** It strips `<link>` tags and the CSS with them, so it can only ever return impressions. Use `curl` for raw source.
- **Impressions instead of extracted values.** Describing a reference as "restrained" or "warm" is not a constraint — you can write it down and still drift anywhere. Fetch the stylesheet, pull the real type scale, colour count, spacing rhythm, and radius into a design doc, then build only from those values. Numbers cannot be argued with; adjectives can.
- **Over-correcting away from the user's references.** Told a draft "looks like AI slop," the reflex is to abandon the whole aesthetic and go bold. But the aesthetic was the user's taste; the draft was just empty. The result is a distinctive page that looks nothing like what they asked for — which is a worse failure, because now their taste is gone too. Put an idea *into* their aesthetic instead.
- **Confusing minimal with generic.** Quiet, light, typographic sites are not inherently default. They are default when they have no spine. Add the thesis and the structural device; keep the calm.
- **Letting the headline enter by default.** A line spliced out of the README on iteration one will survive every subsequent redesign unchallenged, because each later round is about visuals. It looks considered but nobody ever chose it. Offer 3–5 headline options with sources labelled, and get a decision before building.
- **Coasting on copy.** A page can pass every visual check and still read as machine-written in its first sentence. The em-dash enumeration mid-sentence is the loudest tell; "end to end" and "real" are the most common filler.
- **Lifting copy from the README.** It feels like using real content, but docs prose is written to be complete and page copy is written to land. Rewrite it.
- **Copy that repeats what the design shows.** Listing six roles in the intro when the table below lists all six undercuts the visual idea instead of setting it up.

## Best Practices
<!-- Document what works well -->

- **Ask "any sites you like the look of?" early.** It is the easiest question for a non-designer to answer and it is where their taste enters the project.
- **Name the signature move out loud before building.** If the sentence "this design hangs on ___" cannot be finished, there is no direction yet.
- **Write the answer to the distinctiveness question before shipping.** Forcing it into words catches the generic version that "looks fine" at a glance.
